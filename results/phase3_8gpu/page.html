0Background

Earlier pages: Phase 1 Judge Report · Phase 2 Drafter Swap · Phase 3 Re-draft, first run on a shared 4-GPU host (its timings are void; superseded by this page).

  • The system. The target is the frozen MoE SDAR-30B-A3B-Chat-b32 (48 layers × 128 experts, 8 per token; text is written in blocks of 32). A small drafter, SDAR-1.7B-Chat-b32, fills every slot of a block (8 steps); a judge — the same frozen 30B with a trained LoRA — reads the block and commits the slots it is confident about (p > 0.95), keeps agreed-but-unsure drafts and re-masks the rest, pass after pass, until the block is committed.
  • Phase 1 (report) trained that judge LoRA (r32 on q,k,v,o; 128M tokens). Without expert pooling its accuracy matches the plain 30B within noise on 7 of 7 benchmarks, while the 30B needs 1.30–1.41× fewer passes per block. That setup — SDAR-1.7B drafter + frozen 30B with the trained 128M judge, no pool — is the base on this page.
  • Phase 2 (report) swapped the drafter (CoDA-1.7B, Qwen3-0.6B) with the same judge. On the Phase 1 machine the base ran 1.22× faster than the plain 30B in tokens per second (all 7 benchmarks); neither swap beat SDAR-1.7B (0.89–1.03× the base).
  • Phase 3 (this page) keeps the base and adds re-drafting: after every judge pass (rd1) or every second pass (rd2) the drafter re-fills the slots the judge rejected, seeing only the prompt and committed tokens.
  • Why the base was decoded again here. The first Phase 3 run used a rented 4-GPU host shared with another tenant (gpu_frac 0.5), so its times are void. On this unshared 8-GPU machine, identical base work takes 2.2× as long as on the Phase 1 machine: same GPU model, but batch-1 decoding waits on one CPU core and this CPU is slower. A speedup only means something when both setups are timed on the same machine, so the base was re-decoded here with the same code and flags (minus the re-draft). Its outputs match the Phase 1 records token for token, so it is the same base, now timed next to rd1 and rd2.
  • Which baseline the speedups use. Tables 1 and 3 are against the trained setup (SDAR-1.7B drafter + the 30B with the trained 128M judge), measured on this machine. Table 2 is against the plain 30B MoE (“stock”): stock was not decoded here (13 GSM8K items only), so its speedups multiply two numbers, Phase 2’s base over stock (Phase 1 machine) and rd over base (this machine).

6How each number is measured

  • Time per item: torch.cuda.synchronize() + time.perf_counter() around the whole decode (prompt prefill, every judge, drafter, re-draft and KV-flush forward), as in every earlier phase; tokenisation, scoring and record writing are outside it.
  • Tokens per second = Σ tokens ÷ Σ seconds over items, never a mean of per-item rates. Total generation time = Σ seconds. Wall = a run’s start to finish on 8 GPUs.
  • GPU-active time = NVML GPM GRAPHICS_UTIL between two counter samples taken just before and after each item (outside the timed span) × that interval. GPU-only tokens per second = Σ tokens ÷ Σ GPU-active seconds.
  • Speedup over base (Tables 1, 3) = rd tokens per second ÷ base tokens per second on the same items, both on this machine: wall-clock seconds, or GPU-active seconds with the switch on GPU-only. Speedup over stock (Table 2) = A × B, A = base over stock on the Phase 1 machine (Phase 2 page), B = rd over base here. Pooled rows use Σ tokens ÷ Σ seconds over all 2,250 items.
  • Passes per block = Σ (30B forwards − prefill − KV flushes) ÷ Σ blocks. Expert loads per token = Σ unique (layer, expert) loads ÷ Σ tokens. Experts per 30B forward = Σ unique loads ÷ Σ 30B forwards; per judge pass = Σ judge-pass loads ÷ Σ judge passes.
  • Settings: base = --drafter d32 --draft s8 --judge full --adapter <128M> --judge-diag; rd1 / rd2 = base + --full-redraft-every 1 | 2. JetLM/SDAR-30B-A3B-Chat-b32 @ c351bbc, SDAR-1.7B-Chat-b32 @ 2c83c05, judge LoRA hash 35805974; block 32, threshold 0.95, no expert pool, batch 1, one process per GPU, 8 shards items[k::8].

7Why re-drafting gains so little

rd1 and rd2 cut the judge passes by 1.17× and 1.18× (all 7 benchmarks pooled), yet the total decode time on the same items is only 1.030× and 1.081× shorter. This section splits that time by forward kind and follows what the re-draft does pass by pass, on all 2,250 items per setup. Every rd and base number is read from this machine’s per-item records; the cost-model projection, the Phase 2 figures and the probe figures are marked with their source. The analysis is code/phase3_8gpu/redraft_why.py; its numbers are in results/phase3_8gpu/redraft_why.json.

  • The saving is real but small. 1.17× fewer judge passes is a 15% cut. It frees 4.4 h (rd1) and 4.5 h (rd2) of the 38.4 h the base needs for all seven benchmarks (Table 8, Figure 1).
  • Re-drafting spends much of it again. rd1’s re-draft forwards take 2.86 h, 64% of the judge time it saved; rd2’s take 1.40 h (31%), because it re-drafts half as often for the same cut in passes (1.18× against 1.17×).
  • Per-block fixed costs do not shrink. Every block pays one KV flush (a full 30B forward, about 516 ms), the first 8-step draft and its share of the prompt prefill: 9–24% of base time per block. rd’s longer outputs add blocks, so these grow slightly (Table 9).
  • Little crosses from the judge to the drafter. At a re-draft the drafter sees the prompt and the committed tokens only: tentative tokens are hidden as [MASK] (da_decode.py:776), and the judge’s choice, the rejected token and the probabilities are not passed in. 27.3% of rd1’s re-drafted tokens are the token the judge had just rejected; 19.4% are the judge’s own choice (Table 11).
  • Agreement earns nothing at commit time. A slot commits only when the judge’s own probability is above 0.95 (da_decode.py:670). Blocks that need more than 10 judge passes take 42–92% of the base’s passes. In them, re-drafting multiplies the slots where the judge agrees with the draft but stays at or below 0.95 by 2.4–3.9×, while commits per pass rise only 10–20%, and 31–51% of those passes still commit only the one forced slot (Table 12).
  • Tokens per second flatters rd1. rd1 sends 233 items to the length cap (base 147, rd2 177), and 128 of those 233 loop. Text that runs to the cap is cheap to decode: on IFEval, capped base items ran at 9.7 tok/s against 2.9 tok/s for items that ended at EOS. On items that end at EOS in both runs, rd1’s IFEval speedup is 1.020× instead of 1.192× (Table 10).
  • This machine does not set the ceiling. A drafter step costs 21.15 ms here against 494.1 ms per judge pass; on the Phase 1 machine 9.32 ms against 218.6 ms. Both ratios are 4.3%, and the frozen cost model projects 0.96–1.19× for rd over base on the Phase 1 machine (results/phase3_8gpu/PROJECTION.md).
  • Against Phase 2. On the Phase 2 page’s own measure (30B expert loads per token against stock) rd1 and rd2 reach 1.43–1.76×, above the base (1.24–1.33×) and every no-pool Phase 2 arm on all seven benchmarks. Phase 2’s pooled arm (the r3_B judge with the DES48 expert pool) stays ahead once drafter forwards are charged: 1.32–1.42× against rd2’s 1.20–1.24× on the four benchmarks it ran. The pool cuts the experts in every forward, while re-drafting adds drafter forwards; Phase 3 runs without the pool by design (Table 13).

8Feeding the judge’s verdict back to the drafter

The obvious next step is to let the judge tell the drafter what it wanted: write the judge’s choice into the re-masked slots, or give it to the drafter as context. In its raw form that would bring back the next-slot copy, the old failure where the 30B answers a filled slot i with the token of slot i+1. The drafter is not the risk: it only ever predicts at [MASK] slots, and its tokens are only drafts until the judge clears 0.95. The judge is.

  • Where the copy comes from. SDAR was trained to predict only at [MASK] slots. At a filled slot the stock 30B outputs the next slot’s token 88–94% of the time (88% with the draft in the block, 94% with the final tokens, over slots that have a next slot; docs/EXPLAINER_DRAFT_ALIGNED_TRAINING.md section 3): Qwen3’s next-token head showing through. The trained judge removed most of it: at draft slots its choice equals the next slot’s token 6.5% of the time in base, 8.4% in rd1 and 7.6% in rd2.
  • Why a raw fill is still risky. A copy always disagrees with the draft, so what is left of the habit sits in exactly the slots a fill would write: 12.3% of the judge’s disagreements at draft slots in rd1 name the next slot’s token. Written into the block, each reads as a doubled token. In the AB probe (docs/DRAFT_ALIGNED_DESIGN_2026-09-06.md 7.2), given draft tokens as context, the untrained model confirmed 76% of the drafter’s wrong tokens above 0.95, and the judge is a small LoRA on that model, so a later pass could confirm the double.
  • What the counters cannot separate. At [MASK] slots, where SDAR was trained and has no copy habit, the judge names the next slot’s token even more often: 21.9% in base and 28.1% in rd2 (rd1 re-drafts after every pass, so its judge never reads a [MASK] slot). Most of these are probably correct, because a draft that is off by one position needs exactly that fix. A guard can therefore skip such a candidate but cannot tell a copy from a repair.
  • The loop risk is already visible. rd1 raises the looping outputs from 77 to 142 (rd2 115) without passing a single judge token to the drafter. Single-token stutter did not rise the same way: adjacent repeated words per 1,000 tokens fell on 5 of 7 benchmarks under rd1 and rose on MATH-500 and MBPP (7.61 → 7.49 pooled).

9What is measured on this machine, and what the tags in Table 2 mean

  • Every rd speedup against the base is measured on this machine. rd1 and rd2 are compared with the Phase 1 base (SDAR-1.7B drafter + the 128M judge), re-decoded here on all 2,250 items; its outputs match the Phase 1 records token for token on 2,250 of 2,250 (Table 0). Table 1, the rd columns of Table 3, the “base on this machine” rows of Table 6 and sections 7–8 use only these runs: no older timings and no source tags.
  • The tags in Table 2 concern stock only. Stock is the plain 30B with no drafter and no judge, added in Table 2 as a second reference at the project lead’s request. It is not the Phase 1 base, and it was not re-decoded on this machine.
  • Where stock’s timings come from. Stock was decoded on all seven benchmarks, but not on this machine (apart from the 13 setup items below). IFEval-541 ran on an RTX PRO 6000 Blackwell Server Edition (29 Sep), the GPU model the Phase 1 base ran on: its A is MEASURED. The other six ran on an RTX PRO 6000 Blackwell Workstation Edition (5–8 Sep). Seconds from that box cannot be set against the Phase 1 machine’s, so for those six the Phase 2 page estimated stock’s time on the Phase 1 machine from stock’s 30B expert-load count and that machine’s measured time per expert load: STOCK COMPUTED. MOSTLY COMPUTED marks the All-7 row (1.214×), where six of the seven inputs are such estimates.
  • The 13 GSM8K items (MEASURED HERE) are not a baseline. They are the only stock items decoded on this machine (RTX PRO 6000 Blackwell Server Edition, 7 Oct), from a setup check stopped after 13 items, and serve only to spot-check A. On them the base is 1.214× faster than stock here, against 1.260× for A on GSM8K, so the chained stock speedups may be about 4% high; 13 items is a small sample. That this 1.214× and the All-7 1.214× both round to the same three decimals is a coincidence.
  • Exact without any timing. Stock’s accuracy and its 30B expert loads per token do not depend on the machine, so those comparisons in Table 2 are exact.
  • Scaling to the Phase 1 machine is projected, not measured. The frozen cost model gives 0.96–1.19× for rd over base there (results/phase3_8gpu/PROJECTION.md).
  • Removing the tags takes one of two things, and neither has been done: decode stock on this machine next to base, rd1 and rd2 (about 6.7 h on 8 GPUs, an estimate from the base’s 5.4 h here scaled by A), or drop Table 2’s speed columns and keep its accuracy and 30B-work columns.
