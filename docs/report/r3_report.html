why

Why a new recipe

r3_A's holdout accuracy stopped moving after epoch 1 while its certainty term kept sharpening the distribution (the r3_A section below, “Why the curves flattened”, has the full diagnosis). Two things in the plateau probe made that a recipe problem rather than a data problem.

  • Confident overrides were not precise enough to commit. Where the draft was present and wrong (holdout_pass1|all|draft_bad), the slots r3_A committed at p > 0.95 were right only 77.5–81.2% of the time across steps 700, 1000, 1400, 1500 (code pool: 74.2–78.0%). A single wrong committed token breaks a program.
  • Confident confirms degraded as training went on: precision on committed draft_ok slots went 99.1% → 96.7% over the same checkpoints, while the confident fraction kept rising. The β=2 certainty term was buying confidence, not correctness.
  • So r3_B changes the objective, not the data: the same 22,734-example split, the same LoRA, initialised from r3_A's epoch-1 weights, with a weaker certainty term, an explicit calibration loss on the decoder's commit confidence, and extra weight on the override slots that matter for code.
loss

The loss, before and after

r3_A (original)

L = (1/n) Σ_i CE(z_i, T_i) + β · (1/|C|) Σ_(i∈C) H(softmax(z̃_i / τ)) C = { i : argmax z_i = T_i }, β = 2, τ = 0.5, z̃ = logits with the [MASK] column removed

r3_B (calibrated)

L = Σ_i w_i · CE_i / Σ_i w_i weighted cross-entropy + β · (1/|C|) Σ_(i∈C) H(softmax(z̃_i / τ)) same dParallel certainty term, β = 0.5 + λ · Σ_i w_i · BCE(p_i, y_i) / Σ_i w_i calibration, λ = 1 p_i = max softmax(z̃_i) top-1 probability with [MASK] suppressed: the decoder's commit confidence y_i = 1[ argmax z̃_i = T_i ] did that commit turn out right w_i = 1 [MASK] slots and confirms = 2 override slots (draft present and wrong) = 3 override slots in the code pool

The BCE term is a proper scoring rule on the exact scalar the decoder thresholds at inference, so a slot that is committed at 0.97 is trained to be right 97% of the time, in both directions. The weights move the CE mass toward the decisions that break programs. idea

Why a judge, and what it is

SDAR-30B-A3B writes a block of 32 slots at a time. Each pass it commits only the slots whose top token clears 0.95, so a block takes 8–12 full MoE forwards (stock: 8.26 passes/blk on HumanEval, 11.93 on MBPP, 10.06 on GSM8K-500; RESULTS.md §1). The work is repeated passes over mostly-right guesses.

A 1.7B drafter with the same tokenizer can fill the whole block in 8 cheap steps. The big model should then only have to judge each drafted token: keep it, or replace it. The stock model cannot do that. At a filled slot it echoes the next token (93.6% of slots), because SDAR is trained only on [MASK] slots. The in-distribution workaround is sycophantic: it confirms 76% of the drafter’s wrong tokens at > 0.95 and decodes at 67.0% against 95.0% (docs/EXPLAINER_DRAFT_ALIGNED_TRAINING.md §3). Judging a draft is a skill the frozen model lacks. No threshold or vote can add it; training has to.

The judge. A LoRA on the attention projections, plus a learned 2,048-dim draft flag added to the input embedding of every tentative draft slot. The LoRA delta applies only at flagged slots, and the router gates stay frozen. A forward with no flagged slot is therefore bit-identical to the stock model, and the step-0 identity check in train.log confirms it: {'states_checked': 8, 'flagged_slots': 0, 'lora_identity_at_zero_flag': True, 'draft_embed_zero': True}. At inference (--judge full --draft s8) the judge reads the draft-filled block and commits the slots it is confident about. DES32/DES48 further restrict each forward to a 32- or 48-expert pool voted from the block, which cuts expert loads.

One training example

An example is one (item, block) pair. Its state is re-drawn every time the example is visited (code/draftalign/dataset.py):

  • with probability 0.4, nothing is committed: the pass-1 state the judge meets at inference;
  • otherwise a recorded denoising pass is drawn and everything the stock trajectory had committed before it is fixed;
  • open slots hold the drafter’s token with probability 1 − m and [MASK] with probability m, where m ~ U(0, 1); with probability 0.3, every open slot holds the draft (the exact inference regime); all-mask states are off (0.0);
  • the prefix is clean: the prompt plus the final tokens of earlier blocks, exactly what the KV cache holds at inference.

The loss

L = (1/|O|) Σ_(i∈O) −log p_i(T_i) cross-entropy on every open slot + β · (1/|C|) Σ_(i∈C) H(softmax(z_i / τ)) certainty forcing, only where already right C = { i ∈ O : argmax p_i = T_i }, β = 2.0, τ = 0.5, [MASK] column removed from H

Targets T are the final tokens of the stock pipeline’s own correct decodes, not ground-truth text. The judge learns to reproduce what stock would have written, in fewer passes. The certainty term (dParallel) pushes already-right slots past the 0.95 commit threshold.

Accuracy climbed through epoch 1 and then stopped: +0.06 ± 0.16 pts per 100 steps from step 700 to the stop. The loss did not get worse and the model did not memorise; it kept becoming more confident without becoming more correct. 4 · Mechanisms: hypotheses and the evidence for each

None of these is proven by a controlled ablation. Each is tied to what the current data shows, and its verdict updates as the probe and the resumed run land.

(a) The override skill saturates, or needs signal the adapter cannot reach partly: flat overall, but code overrides still improve

The trainable part is a LoRA on attention only (q, k, v, o; r 32; 26.7 M parameters) plus the draft flag. Experts, router gates, embeddings and the head are frozen. Confirming a right draft mostly needs attention to trust the slot. Overriding a wrong one needs the frozen expert path to produce a better token from the changed context, which is a harder function to move with attention alone.

Evidence: Override accuracy is 9.1% for stock, 25.7% at step 700 and 26.5% at step001500 (+0.7 pts after epoch 1). Confirm accuracy is 16.4% / 86.9% / 86.1% (−0.8). On override slots the argmax keeps the wrong draft 17.4% of the time at step 700 and 17.5% at step001500. The aggregate hides a split. Per pool, override accuracy from step 700 to step001500: code (OpenCodeInstruct) 34.0% → 42.0% (+8.0 pts, n=388); maths (GSM8K) 38.8% → 36.6% (−2.2 pts, n=822); verifiable IF 12.6% → 12.9% (+0.4 pts, n=1,059). So the skill has not saturated everywhere: code overrides keep improving after epoch 1, while the largest group, IF overrides, sits near its floor. That reads more like target ambiguity in free-form prose (c) than a capacity cap on the adapter.

Would falsify it: override accuracy still climbing after epoch 1 while overall accuracy is flat, which would mean confirms had regressed instead. Only a LoRA-on-MLP or higher-rank arm tests the capacity half directly.

(b) The certainty term keeps sharpening after CE stops improving consistent with the data

The loss adds β = 2 × the entropy (at τ 0.5) of slots whose argmax is already right. Once CE is flat, the remaining gradient comes largely from this term, which makes right slots more peaked without making more slots right. Because the argmax is right on only about 60% of training slots, the confidence it teaches can spill onto wrong slots.

Evidence: after step 700 CE is flat (+0.002 ± 0.008 per 100 steps), the certainty term still falls (−0.0046 ± 0.0017), and the overconfidence gap widens (+0.13 ± 0.11 pts; 11.9 pts in steps 700–800 to 13.8 pts in steps 1,900–2,000). The training-time holdout shows the same pattern: the confident fraction keeps inching up while argmax accuracy is flat (section above). Precision at τ 0.95 is what turns this into downstream errors. The probe shows it directly: from step 700 to step001500, the share of confirm slots committed at τ 0.95 grew from 64.9% to 69.8%, while the precision of those commits fell from 99.1% to 96.7%. Override-slot commits are 10.5% of override slots at 81.2% precision. More confidence without more accuracy is exactly what this mechanism predicts.

Would falsify it: a β = 0 continuation from step 700 whose accuracy also stays flat. That run would show the plateau is not caused by the term, even if the term inflates confidence.

(c) An irreducible floor: stock-decode targets and masked-future ambiguity plausible for IF prose, not measured

Targets are the final tokens of the stock pipeline’s own correct decodes. At pass 1 many slots are genuinely under-determined: several continuations are fine, and the stock trajectory picked one only after later passes had committed its neighbours. For reference, on 100 GSM8K train prompts the stock model’s own pass-1 argmax already equals the final token at 58.4% of slots (docs/EXPLAINER_DRAFT_ALIGNED_TRAINING.md §1). Pooled train accuracy flattens near 59%. That proximity is suggestive, not proof: the judge also sees the draft, so its ceiling should be higher than stock’s mask-only ceiling.

Evidence: masked-slot accuracy is 47.0% for stock, 57.5% at step 700 and 57.5% at step001500. At step001500, confirm slots are 86.1% right and override slots 26.5%, so most of the remaining error sits in override slots. That error concentrates in IF. IF supplies 1,059 of 2,269 holdout override slots, and they stay at 12.9% right (masked IF slots 34.1%), against 42.0% for code. Free-form IF prose admits many valid continuations, so a target-ambiguity floor is most plausible there and least plausible for code, whose override accuracy is still rising.

Would test it: re-decoding the holdout prompts with the stock pipeline under a different seed or threshold and measuring how often the final tokens themselves disagree.

(d) Data: 22.7k examples reused for 2+ epochs; code coverage against memorisation; data variety still open

The index has 22,734 training examples from 4,294 train items (4,444 minus the 150 held out). By step 1,560 the model has seen each about 2.2 times. The state is re-drawn on every visit (pass choice, mask ratio), so exact repeats are rare, but the targets and prefixes repeat. By items the code pool is the largest (2,344 items, 8,297 blocks), and IF the smallest (690 items, 6,861 blocks).

Evidence: train-split minus holdout accuracy at step001500 is −2.6 pts (probe section 2). A small gap argues against memorisation. It does not rule out that the variety of override situations is what runs out. That would show up per pool, which is why code, still improving, and IF, flat, are worth separating.

(e) The learning rate decayed too far against

The schedule is cosine from 2.0e-5 to a floor of 0.5× (1.0e-5) at step 2,175. The plateau starts around step 700, when the LR was still about 1.8e-5 (90% of peak), and at the stop it is still 1.02e-05. Decay cannot explain a stall that began near peak LR. The opposite is open: an LR too high for the late phase would also produce a flat, noisy loss with a rising gradient norm. A lower-LR tail is cheap to test.

Why code accuracy can improve while the holdout is flat

Downstream, epoch 2 vs epoch 1 on code (paired, same items): MBPP judge +3.5 pts [−1.2, +8.6], exp/token 1,533 → 1,403; MBPP judge + DES48 +5.1 pts [−0.0, +10.5], exp/token 1,266 → 1,150; HumanEval judge +0.6 pts [−4.9, +6.1], exp/token 830 → 793; HumanEval judge + DES48 +2.4 pts [−3.7, +9.1], exp/token 707 → 659. Most of these intervals still include zero, but the direction on MBPP is positive, and expert work fell for every arm listed. The probe points the same way: code override accuracy rose +8.0 pts from step 700 to step001500 (34.0% → 42.0%, n=388 slots). The all-pool holdout barely moved, because IF override slots, the largest group, stayed flat. The two measurements answer different questions.

  • The holdout counts argmax accuracy on 64 pass-1 states, every slot weighted equally. Downstream decoding only commits slots above τ 0.95, and it repeats passes until the block is done. What matters there is precision of the committed set and how errors compound along the trajectory.
  • Sharper confidence on already-right slots (mechanism b) leaves argmax accuracy unchanged, but it changes which slots cross 0.95 and when. That can reduce passes (exp/token fell epoch 1 → 2) and shift errors between committed and deferred slots. For code, one wrong committed token can fail a test, so small precision changes move pass@1 much more than they move slot accuracy.
  • The holdout mixes code, GSM8K and IF slots, 64 states, noise ±~1 pt. A per-pool gain on code can hide inside that noise; part 3 splits it out.

5 · What to try next, ranked

  1. Stricter commit τ, or a low-agreement fallback. This needs no retraining and targets the precision of the committed set, which is what downstream code accuracy depends on. Sweep τ ∈ {0.95, 0.97, 0.99} on MBPP/HumanEval at step001400, and fall back to stock denoising in blocks where the judge overrides many draft tokens. Evidence: override-slot precision at τ 0.95 is 81.2% against 96.7% on confirm slots.
  2. Lower β, or drop the certainty term after epoch 1. After step 700 the term is the only loss component still moving, and the overconfidence gap grows with it (mechanism b). A cheap continuation from step000700 with β = 0 or 0.5 for 300–500 steps tests it.
  3. More adapter capacity: LoRA on the MLP/expert projections, or a higher rank. Attention-only LoRA may cap the override skill (mechanism a). This costs memory and a fresh run, so try it after 1–2.
  4. More, and more varied, code data. Code is where downstream damage lives, and it is the pool whose override accuracy is still moving (34.0% → 42.0% from step 700). More distinct override situations (new prompts, not more epochs over the same 2,344 items) addresses the data half of (a)/(d).
  5. Per-kind loss weighting that up-weights override slots. Overrides are 49% of drafted holdout slots but only 26.5% right, against 86.1% on confirms. Weighting override slots 2–4× pushes the gradient toward the skill that is stuck. Weight by pool as well: code overrides are still learnable, while IF overrides look ambiguous (c), and up-weighting those may teach noise. Watch confirm precision and the keep-draft rate.

How to read, caveats, next steps

How to read the numbers

passes/blk = Σ(n_forward − n_prefill − n_flush) / Σ n_blocks exp/token = Σ unique_expert_layer_loads / Σ n_gen_to_eos acc = 100 · Σ correct / n (vendored OpenCompass evaluators, per item) Δacc = paired on shared idx; bootstrap 95% CI, 2,000 resamples speedup = stock exp/token ÷ arm exp/token, on the same idx

All are block- or token-weighted sums over items (AGENTS.md §8), not means of per-item means. exp/token counts distinct (layer, expert) pairs that actually ran, so under a pool it counts the restricted set. It does not charge the drafter’s own forwards: at 364.64 expert-equivalents each, those erase most of the blind rule’s saving (RESULTS.md §2.1).

Caveats

  • Small subsets. GSM8K is the first 100 of 500 and MATH the first 50. On 50–164 items a single flipped item moves accuracy by 0.6–2 pts; read the CIs, not the point estimates.
  • Uneven schedule. Training stopped at step 1,560 (2.2 epochs) at 08:16 IST and resumed from step001500 at 09:53 IST with the same recipe and the same 2,175-step cosine. It keeps running on that schedule until the server shuts down at 12:20 IST, with a checkpoint every 100 steps pushed to HF (step 2,000 ≈11:45 IST, step 2,100 ≈12:07 IST). Checkpoints after step 1,400 have no downstream eval. Steps 1,510–1,560 were trained twice; the charts keep the resumed run’s rows.
  • Targets are stock decodes. The best a perfect judge can do is match stock accuracy at fewer passes, so a positive Δacc is noise or luck, not a skill the objective teaches.
  • Two stock sources. Stock rows mix the team’s block-32 records with this wave’s new stock decodes (HumanEval DES32/48 and GSM8K plain stock). Both run the same code and model revision, and every comparison is paired on idx.
  • Previous round is documentation only. T2b step 3057 had a different mix, batch and initialisation; it is not an ablation of r3_A.
  • Scoring verified. An earlier socket-path bug in the code-set scorer is fixed. The fixed sandboxed scorer re-scored four older team cells (HumanEval and MBPP; stock and the previous round’s judge + DES48) with 0 item mismatches on 842 items. Decode config is identical to the team’s older runs: model revision, s8 drafter, full judge, τ 0.95, DES pool rule and splits. A scored record with score_error would still be treated as invalid, not incorrect.
